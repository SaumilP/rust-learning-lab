# Java-to-Rust Migration Checks

Use these short checks after reading the comparison material. They verify a mental-model shift; they are not a replacement for the runnable lessons linked in [CANONICAL_RUST_LINKS.md](CANONICAL_RUST_LINKS.md).

| Focus | Java mental model | Rust mental model | Difference to notice | Common mistake to avoid | Check yourself | Canonical lesson |
|---|---|---|---|---|---|---|
| Garbage collection and references | Objects may have many references; the garbage collector eventually reclaims unreachable objects. | A value has an owner, and a move, borrow, or shared owner must be explicit. | Rust determines validity from ownership and borrowing, rather than tracing reachability. | Treating a `String` assignment as another reference to the same value. | Explain why `let second = first;` prevents a later use of `first` when `first` is a `String`, and name two ways to keep both values usable. | [Ownership](../../01-core-fundamentals/ownership/README.md) |
| Borrowing and mutation | Any reference may be used to read or mutate an object when the API allows it. | `&T` shares read access and `&mut T` grants exclusive write access for a limited scope. | Exclusivity is checked before the program runs, not coordinated by convention. | Adding `clone()` before considering a shorter borrow or a different API boundary. | Sketch a function that changes a `String` without taking ownership, then explain why two simultaneous mutable borrows are rejected. | [Ownership](../../01-core-fundamentals/ownership/README.md) |
| Classes, interfaces, and inheritance | Classes combine state and behavior; interfaces and inheritance often provide polymorphism. | Structs hold state, enums model alternatives, and traits describe capabilities. | Traits do not create a shared object layout or inherited implementation state. | Rebuilding a class hierarchy with `Box<dyn Trait>` before deciding whether a generic or enum fits. | Choose between an enum, a generic trait bound, and a trait object for a payment method chosen from a fixed set at runtime. State why. | [Traits and polymorphism](../../06-intermediate-rust/traits_and_polymorphism/README.md) |
| `null` and `Optional<T>` | A reference can be `null`; `Optional<T>` is used where absence is made explicit. | `Option<T>` makes absence part of the type and is handled with matching or combinators. | The absence case is visible in the function signature and must be considered at use sites. | Calling `unwrap()` where absent data is normal input. | Write the return type for a lookup that may not find a user, then describe how the caller should handle both outcomes. | [Result and recoverable errors](../../02-standard-library/error_handling_basics/README.md) |
| Exceptions and `Result<T, E>` | Failure may be represented by checked or unchecked exceptions that change control flow. | Recoverable failure is returned as a value, usually `Result<T, E>`, and `?` propagates it explicitly. | Rust callers can see failure in the return type; panic is not a substitute for expected errors. | Translating every `catch` block into `unwrap()`. | Convert a Java file-reading method that throws `IOException` into a Rust signature, then explain what `?` does to the error. | [Result and recoverable errors](../../02-standard-library/error_handling_basics/README.md) |
| Streams and iterators | A stream pipeline processes collection elements, often without exposing ownership details. | Iterators may consume values, borrow them, or yield mutable references. | The iterator method selected changes what remains usable after the pipeline. | Reaching for indexing or cloning when `iter`, `iter_mut`, or `into_iter` expresses the intent. | For a `Vec<String>`, choose the iterator form that prints values without consuming the vector and the one that transfers the strings into a new collection. | [Collections](../../02-standard-library/collections/README.md) and [iterator patterns](../../02-standard-library/iterator_patterns/README.md) |
| `synchronized`, executors, and thread pools | Shared mutable state is commonly guarded with `synchronized`, locks, or concurrent collections. | Thread transfer and sharing require types that satisfy `Send` and `Sync`; synchronization primitives still protect shared mutation. | Rust prevents many invalid sharing arrangements at compile time but does not remove the need to design for contention and deadlocks. | Assuming `Arc<Mutex<T>>` is the default answer to every concurrent design. | Describe when a channel is clearer than a shared `Mutex`, and name the wrapper commonly used when several threads own the same value. | [Concurrency introduction](../../10-real-world-rust/concurrency_intro/README.md) |
| `CompletableFuture` and virtual threads | Futures and lightweight threads express work that completes later while an executor schedules it. | Futures are inert until polled by a runtime; `async` code should avoid blocking its executor threads. | Rust async is a cooperative execution model, not a direct replacement for either Java abstraction. | Calling a blocking operation inside an async task without moving it to an appropriate blocking context. | Explain why creating a Rust future does not necessarily start work, and identify the boundary where a blocking database client belongs. | [Advanced async overview](../../07-advanced-concepts/advanced_async/README.md) |
| Maven and Gradle | A build tool resolves dependencies, runs tests, and organizes project tasks. | Cargo defines packages and dependencies and provides a consistent command-line workflow. | Cargo manifests describe a package directly; its conventions differ from Maven coordinates and Gradle build scripts. | Treating `Cargo.lock` as a hand-maintained manifest or adding dependencies before checking whether the standard library fits. | Name the Cargo command for a test run and the two files that distinguish package configuration from resolved dependency versions. | [Tooling and quality](../../03-tooling-and-quality/README.md) |
| Dependency injection and composition | A framework often constructs an object graph and supplies collaborators through containers and annotations. | Constructors, structs, traits, and explicit wiring make dependencies visible at the composition root. | Rust has DI libraries, but ordinary explicit composition is usually the simplest starting point. | Hiding every dependency behind a trait object or global service locator. | Design a `Service` that depends on a repository: show which dependency should be a field, where it is constructed, and when a trait bound is justified for testing or substitution. | [Intermediate Rust](../../06-intermediate-rust/README.md) |

If an answer feels like a syntax substitution, return to the comparison documents and identify the ownership, error, or execution-model difference first. That distinction is the point of the track.
